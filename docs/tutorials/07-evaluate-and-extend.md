# 5. 결과 해석과 다음 학습 실험

**완료 기준:** 한 번의 리플레이와 다판 통계가 각각 무엇을 보여주는지 구분하고, 규칙이나 보상 변경 후 관찰 결과를 재현 가능하게 기록합니다.

## 먼저 확인하고 싶은 것을 정하기

학습 실습에서는 먼저 질문을 작게 정합니다. “BT 분기가 바뀌었나?”, “규칙을 바꾼 뒤
명령과 궤적이 달라졌나?”, “새 정책이 어떤 상황에서 다른 행동을 하나?”는 초기화와
리플레이를 확인해 탐색할 수 있습니다. “어느 조종기가 일반적으로 더 뛰어난가?”는
훨씬 많은 통제와 증거가 필요한 별도의 주장입니다.

| 질문 | 알맞은 확인 방법 |
|---|---|
| BT의 어느 가지가 실행됐나? | 노드 trace와 리플레이에서 분기·행동 확인 |
| 규칙 수정이 반영됐나? | 작은 설정에서 출력 명령과 궤적 비교 |
| 새 정책이 학습 중인가? | 보상·진행 곡선 관찰 후 별도 시드에서 다시 실행 |
| 결과가 초기 위치에 민감한가? | 여러 seed로 반복하고 에피소드별 결과 분포 확인 |
| 어느 파일럿이 더 우수한가? | 충분한 반복·통제·불확실성 분석이 필요한 더 강한 주장 |

분기 테스트 통과는 코드 경로가 의도대로 실행된다는 근거입니다. 한 리플레이는
그 판에서 관측된 행동을 보여줍니다. 이 둘만으로 반복적인 성능 우위나 현실 전투
효과를 입증하지는 않습니다.

## 학습 실험을 비교 가능하게 남기기

- **같은 초기 조건:** 파일럿을 비교한다면 같은 seed 목록을 사용합니다.
- **한 번에 하나:** 파일럿·팀 규모·상대 행동·물리를 동시에 바꾸지 않습니다.
- **여러 관찰:** 승패 외에 기체 손실, 교전 시간, 충돌과 리플레이의 기동을 함께 봅니다.
- **분포와 원자료:** 평균 한 숫자만 남기지 말고 에피소드별 JSON/CSV와 설정을 저장합니다.
- **재현 명령:** 명령줄, 시작 seed, 에피소드 수와 적용한 커밋을 기록합니다.
- **주장 범위:** 표본이 작으면 관찰을 기록하고, 보편적 우위로 일반화하지 않습니다.

## 실습 노트에 남길 것

프로젝트의 `scripts/compare_assigners.py`는 `--out-dir`을 주면 비교 결과를 한 디렉터리에 기록합니다.
알고리즘 전환이 보이는 초기 할당 그림과 리플레이도 재사용 가능한 증거입니다.

결과 페이지에 최소한 다음을 적습니다.

1. 실험 목적과 비교한 가설
2. 팀 규모·파일럿·상대 행동·물리 백엔드
3. 알고리즘 설정과 통신/센싱 반경
4. seed 범위와 판 수
5. 승리·격추·손실·할당·통신 관련 결과
6. 한계와 이번 결과로 말할 수 없는 것
7. JSON/CSV, 그림/리플레이, 재실행 명령

## 다음 학습 질문

- 어떤 관측 채널이 규칙 기반 파일럿과 학습 정책의 행동 차이에 연결되는가?
- BT 우선순위를 바꾸면 경계 복귀와 추격 중 어느 결정이 먼저 실행되는가?
- 보상 가중치를 바꿨을 때 학습 행동과 교전 결과가 각각 어떻게 달라지는가?
- pointmass와 JSBSim에서 같은 명령이 어떻게 다른 기체 반응을 만드는가?
- 여러 seed에서 반복되는 변화와 한 판에만 나타난 우연한 변화는 무엇인가?

## 추천 확장 순서

1. 먼저 `combat.yaml`에서 실험을 재현합니다.
2. 기존 구현을 수정하기 전에 관측과 테스트를 추가합니다.
3. 작은 설정·짧은 실행으로 정확성을 확인합니다.
4. 전체 paired 실험과 리플레이를 생성합니다.
5. 사이트 튜토리얼이나 결과 문서에 발견한 제한과 근거를 기록합니다.

## 규칙 기반 AI Pilot을 bottom-up으로 만들기

전술 전체를 한 번에 작성하지 말고, **기동 하나를 구현하고 검증한 다음
`combat.xml`에서 조합**합니다. F-16 모델이 `HighYoYo`나 `Break Turn` 같은
전술을 내장 제공하는 것은 아닙니다. 시뮬레이터가 제공하는 상태와 제어 경로를
사용해 기동 로직을 직접 작성해야 합니다.

### 1. 먼저 데이터와 명령을 파악하기

BT는 매 decision step마다 `info` 사전에서 현재 상태를 읽습니다. `range`는
거리(m), `bearing`은 내 기수 기준 좌우 방위(rad, 오른쪽 양수), `closure`는
접근 속도(m/s, 가까워질수록 양수), `dh`는 상대 고도에서 내 고도를 뺀 값(m)입니다.
자신과 상대의 속도·자세·조준각·무장 영역 여부도 사용할 수 있지만, 훈련 측과
고정 측 Brain이 받는 항목은 완전히 같지 않으므로 실제 전달 정보는
`envs/swarm_pursuit.py`의 `_trained_info`와 `_fixed_info`를 확인합니다.

기동 출력도 구분합니다.

- 기존 `Pursue`/`Break`는 이산 방향·속도·고도 목표를 냅니다.
- 직접 연속 제어 정책은 JSBSim에 roll/pitch/rudder/throttle 입력을 냅니다.
- 현재 `combat.xml`의 `TurnTowardTarget`은 목표 뱅크·하중배수·스로틀을 담은
  `ManeuverIntent`를 냅니다. 거리별 스로틀은 목표 속도 제어기가 아닙니다.

### 2. 기동을 하나씩 시험하기

추천하는 첫 기동 묶음은 `LevelFlight` → 목표 뱅크 유지 → 목표 헤딩 선회 →
목표 속도 유지 → 표적 요격입니다. 각 기동마다 다음을 정합니다.

| 기록할 항목 | 예시 |
|---|---|
| 입력 | 목표 뱅크, 상대 방위, 거리, 속도 |
| 기대 동작 | 좌우 대칭, 제한된 뱅크, 지정 속도 접근 |
| 성공 기준 | 도달 시간과 오차, 고도·속도 변화, 오버슛 여부 |
| 시험 방법 | 고정 초기 상태의 단위/제어 통합 테스트와 리플레이 |

시험은 작은 고정 시나리오부터 시작합니다. 예를 들어 표적을 내 왼쪽에 두고
시작해 좌선회 방향과 뱅크 응답을 확인한 다음, 오른쪽 배치에서도 대칭 결과가
나오는지 테스트합니다. 적기가 필요한 시험도 처음에는 일정한 직선 비행처럼
단순한 표적으로 충분합니다. 특정 기동을 시험하는 데 현실적인 적 전술 전체가
필요한 것은 아닙니다.

### 3. 검증된 기동을 주 BT에서 조합하기

각 기동의 입력·출력과 제어 반응을 따로 확인한 뒤, 검증된 Action을
`swarm_aircombat/bt/trees/combat.xml`에서 조건과 우선순위로 연결합니다. 예를
들어 “표적이 멀면 접근”, “가까우면서 빠르게 접근하면 감속”, “목표가 없으면
안전하게 선회”처럼 규칙을 나눌 수 있습니다. 현재 BT는 기본적으로 스텝마다
다시 평가되므로, 여러 틱에 걸쳐 단계를 기억해야 하는 기동은 별도 상태 관리와
종료 조건을 구현한 뒤 추가합니다.

기동 단위 테스트 통과는 코드가 동작한다는 근거이고, 한 번의 리플레이는 그
초기 조건에서 보인 궤적입니다. 전투 효과를 주장하려면 같은 조건의 기준 파일럿과
비교하고 여러 seed에서 결과를 확인해야 합니다. 현재 `combat.xml`은 상대 방향
선회와 거리 기반 스로틀 조절을 시험하는 초기 예제이며, 목표 속도 유지나
복합 전술까지 검증된 파일럿은 아닙니다.

이제 시뮬레이터를 실행하는 데서 나아가, 규칙을 설계하고 학습 정책을 읽으며
작은 변화를 비교할 수 있습니다. 더 큰 연구 주장은 목적에 맞는 추가 검증이 필요합니다.
